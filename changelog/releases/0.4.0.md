## Why Care?

A fragment URL is a public contract. Someone pastes `…/some-guide#installing-the-cli` into Slack and it has to keep landing on that heading a year later.

We were shipping **two incompatible definitions of that contract**. `lossless-monorepo/site` used `utils/slugify.ts`. Every astro-knots site inlined a different algorithm directly in `AstroMarkdown.astro` — including `packages/lfm-astro/`, the canonical copy-from source, so every new site inherited the divergence.

| heading | `lossless/site` | astro-knots | |
|---|---|---|---|
| `Set_Up the Repo` | `set_up-the-repo` | `setup-the-repo` | differs |
| `-- Notes --` | `notes` | `---notes---` | differs |
| `Deploy to prod.md` | `deploy-to-prod` | `deploy-to-prodmd` | differs |

Neither deduped collisions, so two headings with the same text produced two elements with the same `id` and the second was permanently unreachable. An audit across both content trees found **31 documents** in that state, plus **7 headings slugifying to the empty string** — invalid HTML, all colliding with each other.

## What's New?

**`remarkHeadingIds`**, enabled by default in the `remarkLfm` preset. For every heading it stamps:

- `data.id` — the final, deduped anchor id
- `data.hProperties.id` — so anything that *does* reach rehype behaves
- `data.headingText` — plain text, markup stripped, for button labels and ToC rows

And attaches an ordered outline at `tree.data.headings`, ready to render a table of contents without touching the DOM:

```ts
const tree = await parseMarkdown(md);
for (const h of tree.data.headings) {
  // { id, text, depth, duplicateOf?, synthetic? }
}
```

Three behaviors worth naming:

1. **Collisions get suffixed.** The second `View Logs` becomes `view-logs-2`, and the outline entry records `duplicateOf: 'view-logs'` so the drift is diagnosable rather than silent.
2. **Empty slugs get a positional fallback.** A heading of `✅ 🎉` — or one written in a script outside `[a-z0-9]` — becomes `heading-7` rather than `""`. Ugly, but valid, unique, and stable.
3. **Headings nested in containers are found.** A `###` inside a `> [!info]` callout body gets an id like any other.

## The slug algorithm is deliberately quirky

`slugifyHeading` is **bug-for-bug identical** to `lossless-monorepo/site`'s `slugify`, including the trailing-extension strip and the 3+ dash collapse that preserves intentional `--` separators.

That is a decision, not an accident. That site is the only one with share buttons in the wild, so it holds the only meaningful population of already-published fragment URLs. Matching it exactly means **zero anchors move** where breakage would actually be felt. The 646 anchors that do change (5% of 11,809) are all in astro-knots, which has no share UI — those fragments are internal ToC jumps that regenerate at build.

Collision dedupe is strictly additive on top: it cannot move an anchor that wasn't already colliding, and where it fires, the previous behavior was broken anyway.

Pass your own via `headingIds: { slugify: myFn }`, or opt out with `headingIds: false`.

## No new dependencies

The obvious tools here are `mdast-util-to-string` and `unist-util-visit`. LFM deliberately avoids the latter — `og-fetcher.ts` and `remark-lossless-wikilinks.ts` both say so in comments and hand-roll their walkers to keep the install graph small. This plugin follows suit: about 25 lines of recursive walk and text extraction, versus two more packages on every consuming site.

## What this does NOT touch

`lossless-monorepo/site`'s `slugify` currently serves three different contracts through one function: heading anchors, file slugs (`getReferenceSlug`), and tag normalization (`normalizeTag` — which uses it as an **equality test**, so a change there silently drops posts off tag pages with no error). This release adds a heading-specific slugifier and touches neither of the others. Splitting those apart is real work that deserves its own spec.

## Upgrading

Sites on 0.3.x get anchor ids automatically on upgrade; nothing breaks by adding an `id` to a heading.

To render the share affordance, copy `HeadingAnchor.astro` from `astro-knots/packages/lfm-astro/components/` and update your `AstroMarkdown.astro` heading branch to read `node.data.id` instead of computing a slug.

**Order matters.** Do not adopt the new `AstroMarkdown.astro` before upgrading the package — on 0.3.x `data.id` is `undefined`, so headings would lose their ids entirely until the version bump lands.
