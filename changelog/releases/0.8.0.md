## Why Care?

Some of our sites are written in MDX: posts that drop a chart or a stat block
into the prose. Until now those sites had to render MDX with their framework's
own pipeline, which meant no LFM there: no shared heading ids, no citations, no
callouts, and two render paths to maintain. Now an `.mdx` file goes through LFM
like any other markdown, and its components come along.

## What's New?

- **`mdx` option.** `parseMarkdown(body, { mdx: { filePath } })` parses MDX
  syntax. Turn it on for `.mdx` files only.
- **MDX is a trigger syntax.** Each JSX element becomes a `componentNode` with
  `triggerSyntax: 'mdx'`. Unlike the other triggers it needs no lookup in a
  site's component map: `import` names the file it was imported from, resolved
  against the `.mdx` file's path, so the renderer just renders that file.
- **Props with their real types.** `items={[…]}` arrives as an array. Props are
  evaluated statically and never executed; one that needs code is listed in
  `dynamicProps` instead.
- **Imports leave the content**, recorded on `tree.data.mdx.imports`. Comment
  expressions disappear and fragments unwrap.

## Under the Hood

- Built on `remark-mdx` for parsing, so the syntax is exactly what MDX accepts.
  The new part is what happens after: the static evaluator and the import
  resolution.
- Named `remarkLfmMdx`: a formal remark plugin exists (`remark-mdx`) and we
  behave differently, which puts it in Tier 2 of the naming contract.
- First consumer: edviro-blog, whose 13 articles all parse with every component
  resolved and no dynamic props.
